# Small MLP and effect-modifier signal ablations

These two additive binary experiments reuse the original
`SyntheticEffectModifier` generator, outcome-contrast evaluator, multiround
FedAvg implementation, iterative dsLassoCov-style logistic LASSO and original
Diag/KFAC FedFisher CPU recipes. Existing recipes and result namespaces remain
separate. The new factory setting is `SyntheticMLPSmall`, with one ReLU hidden
layer of eight neurons: `201 -> 8 -> 2`, including biases, **1,634 parameters**.
The existing shallow `(64, 32)` and deep `(256, 128, 64, 32)` networks retain
their settings.

| Setting | Effect-modifier strength | MLP architectures | Method configurations |
| --- | ---: | --- | ---: |
| `small_mlp` | 2.0 | Small only | 10 |
| `weak_signal_1` | 1.0 | Small, shallow, deep | 31 |
| `weak_signal_05` | 0.5 | Small, shallow, deep | 31 |

Each architecture uses all eight original FedAvg settings: local epochs
`1, 5, 10, 30`, each with validation patience and fixed total budget 30. The
budget-30/epoch-30 recipe still has one aggregation round. Learning rate,
momentum, batches, stopping, selection, refitting and random-seed rules are
copied from the comparison protocol. Each architecture also uses the original
standalone CPU Diag and KFAC recipes, including 30 local epochs, 2,000 server
iterations, compression, validation selection and selected-Fisher RNG isolation.
KFAC retains its existing architecture-dependent compression rule.

Each weak-signal setting includes **one** iterative dsLassoCov configuration;
it has no MLP architecture. Its original five folds, 30 lambda values and
2,000-iteration optimizer limit remain unchanged. A numerical limit is not
convergence and cannot produce accepted completion evidence.

Only `dgp.signal_strength` changes for the weak-signal recipes. The outcome
interaction coefficients for `A*X1` and `A*X2` are respectively plus/minus
`signal_strength / sqrt(2)`. Prognostic main effects and confounding strength
both remain 1.0. Outcomes and outcome-dependent non-IID assignments are
regenerated by the original generator; identical datasets across different
signal strengths are not required. Within a signal setting, all methods share
the prescribed data and intervention plans.

Every setting retains all four factorial variants (`control`,
`site_gaussian_shift`, `local_permutation`, `site_gaussian_local_permutation`),
IID and non-IID splits, and the original data/evaluation sizes. The primary
cross-method endpoint is raw-X probability-contrast intervention recovery with
explicit tie handling; logit-contrast recovery remains available separately.
Training, tuning/refitting, aggregation and evaluation costs remain distinct.

The seed-zero pilot comprises 288 requests and 576 scientific units. Formal
scope is seeds 0..299: 24,000 small-MLP units and 148,800 weak-signal units,
172,800 in total. Formal shards are disjoint deterministic sequences at 8 or
16 shards per setting/method/variant. Run IDs begin with
`model_signal_<setting>_<cell>_<variant>_v1_`; old outputs are never reused.

## Implementation and admission

`protocol.py` composes copies of the existing fixed recipes. `runner.py`
dispatches to the existing scientific functions. `artifacts.py` reuses the
immutable timing store and each method family's existing semantic validator.
`acceptance.py` verifies the complete pilot, paired invariants and actual
central producer evidence. Formal publication and runtime both require the
same-source accepted pilot proof; central resource review is still required.
Formal startup revalidates all 576 pilot units and their producer evidence.
This verification adds filesystem work outside measured method fitting time;
operator profiling must account for that startup cost.

The sole execution entrypoint remains the project ServerScheduler adapter.
New task names are `effect-modifier-model-signal-pilot` and
`effect-modifier-model-signal-shard`. The proposal in
`../server_scheduler/model-signal-ablation-v1/` is disabled. No direct compute
CLI or launcher is provided. Development fixture tests are not pilot evidence.

After canonical-source integration, clean source freeze and operator review,
`scripts/prepare_model_signal_requests.py` can prepare an immutable pilot
review bundle. `scripts/validate_model_signal_pilot.py` validates its completed
scientific outputs. The builder's formal mode requires that acceptance proof.
Creating an outbox bundle does not submit jobs or authorize formal execution.

Source belongs in the repository; durable results belong below

logs/caches and request review bundles belong below
